# Hotel Analytics — система коммерческого управления отелем

**Проектирование и разработка прикладной аналитической системы для гостиничного бизнеса.**

[Посмотреть публичную демонстрацию](https://belyakovko.github.io/hotel-analytics-demo/)

> Публичный сайт — обезличенная интерактивная презентация проекта. Описанные ниже архитектура, интеграции и расчётные механизмы относятся к **оригинальному приложению**, а не к упрощённой HTML/JavaScript-демонстрации. Производственный код и данные клиентов в этом репозитории не размещены.

## О проекте

Проект возник из практической задачи: объединить данные о спросе, продажах, бронированиях, номерном фонде, тарифах и планах в единый инструмент принятия коммерческих решений. Вместо набора независимых отчётов разрабатывается управленческий контур:

**Источники → проверка и нормализация данных → показатели и прогноз → выявление отклонений → управленческие решения → оценка результата.**

Цель — управлять загрузкой, ценой и экономическим результатом, учитывая не только объём продаж, но и доступный физический фонд, сроки продаж, динамику спроса и ограничения данных.

## Что реализовано в оригинальной системе

### 1. Оперативный коммерческий обзор
- Показатели загрузки, проданных и забронированных номеро-ночей, выручки, ADR, RevPAR и выполнения плана.
- Годовые и помесячные срезы, сравнение с аналогичными периодами и детализация по тарифам.
- Разделение коммерческой брони и физической занятости номерного фонда.
- Поэтапная загрузка главного экрана: сначала базовый обзор, затем годовой срез и прогноз, после — тяжёлые подробности продаж.
- Серверные агрегаты и предварительно рассчитанные витрины для сокращения времени ответа.

### 2. Аналитика спроса
- Раздельный учёт **уникальных клиентов**, **запросов** и **расчётов стоимости**.
- Запрос определяется как уникальная пара «клиент × календарный день», поэтому несколько расчётов одного клиента за день не раздувают число запросов.
- Анализ интереса к датам проживания, направлениям и тарифам, сопоставление спроса с бронированиями и конверсией.
- Контроль неизвестных идентификаторов и неполных записей: отсутствие данных не маскируется нулевыми показателями.
- Серверная обработка истории источников с постраничным чтением по устойчивому идентификатору строки.

### 3. Продажи и CRM
- Анализ продаж по датам счетов, периодам проживания, тарифам и менеджерам.
- KPI: номеро-ночи, количество счетов, сумма, ADR, средний чек, динамика относительно выбранного периода.
- Отмены анализируются отдельно, чтобы не вычитать их повторно из уже очищенного объёма продаж.
- Раскрытие показателей от месяца к тарифу и далее к сделкам, с сохранением сверки итогов.
- CRM-аналитика по лидам и сделкам с использованием исторических и оперативных источников Bitrix24.

### 4. Управление тарифами и прогноз
- Реестр тарифов с периодами проживания, индивидуальными окнами продаж, планом, текущей бронью, спросом и конверсией.
- Оценка темпа продаж (**pickup**), сопоставление с аналогом прошлого года и определение необходимого темпа.
- Модель прогноза использует несколько горизонтов pickup, темп с начала продаж, исторический аналог, остаток периода продаж и ограничения номерного фонда.
- Распределение ожидаемых дополнительных продаж по датам и категориям с ограничением свободным физическим фондом; пересекающиеся тарифы конкурируют за общий остаток.
- Отдельный расчёт непокрытого тарифами, недоступного и потенциально упущенного объёма.
- Отображение неопределённости: если исходных данных недостаточно, система сообщает об ограничении вместо ложной точности.

**Важное разграничение:** в проекте документированы разные поколения прогнозной логики, включая оперативный слой M0. Их нельзя считать одной и той же моделью или автоматически считать все экспериментальные механики внедрёнными в production.

### 5. Физический номерной фонд и планирование
- Учёт доступности по физическим номерам и календарным ночам, а не только по сумме тарифных планов.
- Обработка пересекающихся размещений, служебного использования, ремонта и бесплатных проживаний.
- Сопоставление номеров с источником размещения и контроль неоднозначных соответствий.
- Разработка единого операционного слоя для согласования факта, брони, фонда и прогноза между разделами.
- Отдельный контур дневного планирования, справочников фонда, версий и согласования изменений.

### 6. Экономика коммерческих решений
- Сценарии изменения цены и объёма продаж.
- Учёт переменных и условно-постоянных расходов в модели планирования.
- Оценка влияния решений на маржинальный результат, а не только на выручку или процент загрузки.
- Сигналы по тарифам, позволяющие выделять направления, требующие управленческого внимания.

## Техническая архитектура оригинального приложения

| Уровень | Использованные решения |
|---|---|
| Web-приложение | **Next.js 16**, **React 19**, **TypeScript** |
| Интерфейс | **Ant Design**, Tailwind CSS, интерактивные таблицы и графики |
| Серверная логика | Next.js server-side rendering, внутренние API routes, предметные библиотеки расчётов |
| Хранение и вычисления | **Supabase / PostgreSQL**, SQL, RPC-функции, индексированные витрины и кэши |
| Источники | **Google Sheets**, **Bitrix24**, справочники и настройки приложения |
| Интеграция с CRM | Bitrix24 BI для исторических срезов, VibeCode API для оперативных данных |
| Доступ | Серверная проверка пользователя, роли и разрешения; закрытые ключи не отправляются в браузер |
| Разработка и выпуск | Git, GitHub, GitHub Actions, миграции SQL, проверки сборки и сценариев, процедуры отката |

### Поток данных

```text
Google Sheets ──→ синхронизация ──→ PostgreSQL / Supabase
Bitrix24 ───────→ BI / API ───────→ серверные адаптеры
Настройки ──────→ тарифы, справочники, правила, планы
                                  │
                    нормализация и дедупликация
                                  │
                       SQL / RPC / кэши / API
                                  │
                    предметные расчётные модули
                                  │
                    Next.js / React / интерфейс
                                  │
                 аналитика → прогноз → решения
```

Секреты интеграций остаются на сервере. Публичный API возвращает агрегаты и разрешённую детализацию; пользовательские права проверяются до выдачи данных.

## Инженерные задачи и принятые решения

**Согласованность метрик.** Для разных источников закреплены общие определения: дата счёта не равна дате создания сделки; запрос не равен расчёту; коммерческая загрузка не равна физической занятости. Отдельно учтена управленческая календарная граница: ночь 31 декабря относится к январю следующего года.

**Достоверность прогноза.** Новые продажи ограничиваются остатком физических номеров по конкретным датам и категориям. Действующая бронь не обрезается искусственно до фонда. Конфликтные и неизвестные состояния сохраняются как диагностируемые состояния, а не превращаются в фиктивную доступность.

**Производительность.** Вместо повторного тяжёлого чтения сырых данных используются предварительные SQL-витрины, RPC и поэтапная загрузка экрана. В проекте проведены измерения производительности и оптимизация запросов. Экспериментальные изменения, не прошедшие приёмку, не переносились автоматически в production.

**Управляемость изменений.** Бизнес-формулы фиксируются вместе с источниками, ограничениями и проверочными примерами. Для миграций предусмотрены проверки, резервные сценарии и откат. Отдельно ведутся карта проекта, карта данных, задачи, решения и документация методик.

**Удобство работы.** Интерактивные таблицы поддерживают сортировку, фильтрацию, раскрытие строк и настройку ширины колонок. Параметры отображения сохраняются в браузере; интерфейс адаптирован для разных размеров экрана.

## Уровень готовности

Проект **не находится на стадии идеи или нарисованного макета**: оригинальное приложение содержит рабочие серверные API, предметные расчёты, интеграции с источниками, аналитические экраны, модели прогнозирования, проверки и техническую документацию.

При этом развитие идёт поэтапно. Часть компонентов уже используется в рабочем контуре, часть реализована и проверена локально, а отдельные направления — в том числе некоторые изменения оперативного слоя, дневного планирования и ускорения обработки спроса — проходят отдельную приёмку либо приостановлены. **Локальная реализация, успешные тесты и развёртывание в production — разные статусы.**
